# Journal Domain

## Overview

Stores daily journal entries keyed by local date (`YYYY-MM-DD`). Each entry has a `raw_text` field (free-form user note or retro summary) and an optional `retro_json` field (structured nightly retrospective generated by `orchestrator/retro.py`). One row per user per day — upsert semantics throughout.

**Design rule:** only the orchestrator crosses domain lines. This file documents everything a future developer needs to maintain the journal domain without reading any other domain.

---

## Data Model

### `journal_entries`

| Column | Type | Notes |
|--------|------|-------|
| `id` | INTEGER PK | Auto-increment |
| `user_id` | INTEGER | Default 1 |
| `date` | TEXT | `YYYY-MM-DD` in local time (from `today_local()`) |
| `raw_text` | TEXT | Free-form text — either the user's own words or the retro's `summary` field |
| `summary` | TEXT | AI-generated 2-3 sentence condensed summary (Sonnet via `save_journal_entry`), nullable |
| `retro_json` | TEXT | JSON string of the structured retro object (see shape below), nullable |
| `created_at` | TEXT | Local time, auto-set on first insert; not updated on upsert |

Unique constraint: `(user_id, date)` — one entry per day. `upsert_entry` replaces all mutable fields on conflict.

---

## Retro JSON Shape

`retro_json` is a serialized JSON object produced by `orchestrator/retro.py` via Sonnet. Schema:

```json
{
  "wins": ["string", "..."],
  "misses": ["string", "..."],
  "patterns": ["string", "..."],
  "tomorrow": ["string", "..."],
  "summary": "string"
}
```

| Field | Type | Description |
|-------|------|-------------|
| `wins` | `string[]` | What went well today — specific numbers, named achievements |
| `misses` | `string[]` | What missed targets and why — specific, not generic |
| `patterns` | `string[]` | Cross-domain connections (e.g. late dinner → poor deep sleep) |
| `tomorrow` | `string[]` | 2-3 concrete action items for the next day (imperative sentences) |
| `summary` | `string` | 2-3 sentence plain-text overview of the day — also stored as `raw_text` |

The retro engine stores `retro_data["summary"]` in `raw_text` and the full object (serialized) in `retro_json`. The `summary` field in `journal_entries` is left `NULL` when written by the retro engine (it's populated only by the interactive `save_journal_entry` tool that calls Sonnet separately).

## Write Paths

There are two distinct write paths into `journal_entries`:

### 1. User-initiated (interactive)

`POST /journal/entry` → `save_journal_entry()` in `tools.py`:
1. Calls Sonnet (`POLISH_MODEL`) to summarize the user's raw text into 2-3 sentences.
2. Calls `upsert_entry(conn, user_id, today, raw_text=user_text, summary=ai_summary, retro_json=None)`.
3. Returns `"Journal entry saved for today."`.

This path populates `raw_text` with the user's words and `summary` with the AI condensation. `retro_json` is not set.

### 2. Nightly retrospective (automated)

`orchestrator/retro.py` → `generate_retro(conn, user_id)`, triggered by the scheduler at 10pm:
1. Fetches cross-domain context (health, finance, tasks, knowledge, today's journal entry if any).
2. Calls Sonnet to generate a structured `{wins, misses, patterns, tomorrow, summary}` object.
3. Calls `POST /journal/entry` with `raw_text=retro_data["summary"]` and `retro_json=json.dumps(retro_data)`.
4. `upsert_entry` merges into today's row (or creates it).

If the user already wrote a note (via path 1), the retro's `POST /journal/entry` overwrites `raw_text` with the retro summary. The user's original words survive only if the retro engine read them from `GET /journal/{today}` and included them in the `[USER NOTE]` context section of the Sonnet prompt.

---

## Evening Scheduler Flow

The scheduler (`scheduler.py`) runs three journal-related jobs:

| Time | Job | Behavior |
|------|-----|----------|
| 10:00pm | `_evening_prompt` | If no entry exists for today: sets `pending_state(type="evening_summary")` and sends Telegram: "How was today? Anything to capture?" |
| 10:30pm | `_evening_followup` | If still no entry: sends Telegram: "Still up? Just a few words about today is fine." |
| 10:00pm | (retro — via `retro.py`) | `generate_retro` assembles full-day context and writes to `POST /journal/entry` |

**Note:** the retro engine and the evening Telegram prompt both run at 10pm. The prompt fires first (checks for a missing entry), then the retro writes the entry. On subsequent scheduler ticks, the followup check at 10:30pm sees the retro-written entry and stays silent.

The `pending_state` row (`type="evening_summary"`) signals to the Telegram bot that the next user message should be treated as a journal entry. When the user replies, the bot calls `save_journal_entry()` and clears the pending state.

## Key DB Functions

### `upsert_entry(conn, user_id, date, raw_text, summary=None, retro_json=None) → None`
`INSERT ... ON CONFLICT(user_id, date) DO UPDATE SET raw_text=..., summary=..., retro_json=...`

All three mutable columns are always overwritten on conflict — partial updates are not supported. Pass `None` for `summary`/`retro_json` to clear them.

### `get_entry(conn, user_id, date) → dict | None`
Returns a single entry dict for the given local date string, or `None` if no entry exists.

### `get_recent(conn, user_id, limit=7) → list`
Returns the most recent `limit` entries ordered by `date DESC`. Default is 7 days.

## API Endpoints

| Method | Path | Description |
|--------|------|-------------|
| `POST` | `/journal/entry` | Upsert today's entry (Sonnet summary generated if `summary` not provided) |
| `GET` | `/journal/recent` | Last 7 entries, ordered newest first |
| `GET` | `/journal/{date}` | Single entry for `YYYY-MM-DD`; 404 if missing |

## Response Shapes

### `GET /journal/recent` (also used by insights engine)
```json
[
  {
    "id": 14,
    "user_id": 1,
    "date": "2026-08-09",
    "raw_text": "Good day overall. Hit protein target and 9,800 steps.",
    "summary": "Hit most health targets. Missed 200 steps.",
    "retro_json": "{\"wins\":[\"Protein 153g\"],\"misses\":[\"Steps 9800/10000\"],\"patterns\":[],\"tomorrow\":[\"Morning walk\"],\"summary\":\"Good day...\"}",
    "created_at": "2026-08-09 22:05:00"
  },
  ...
]
```

`retro_json` is a raw JSON string — parse it client-side if you need structured access. The insights engine reads it as-is and passes the raw array to the LLM context.

### `POST /journal/entry`
```json
{"ok": true, "date": "2026-08-09"}
```

### `GET /journal/{date}` — 404 body
```json
{"detail": "No entry for this date"}
```

## Insights Engine Integration

`orchestrator/insights.py` fetches `GET /journal/recent` and injects the response into the `[JOURNAL — RECENT]` section of the insight prompt:

```python
journal = _fetch("/journal/recent")
if journal:
    sections.append(f"[JOURNAL — RECENT]\n{json.dumps(journal, indent=2)}")
```

The full entry objects (including `retro_json` as a string) are passed to Sonnet. The model reads the `raw_text` and `retro_json` fields to understand recent mood, patterns, and stated intentions.

`orchestrator/retro.py` similarly reads `GET /journal/{today}` at step 5 of the retro flow to capture any user-written note for the `[USER NOTE]` section. This ensures the retro incorporates what the user actually said before generating the structured retrospective.

## Known Issues / Gaps

- **Upsert clobbers user note** — if the user writes a journal note at 9pm and the retro engine fires at 10pm, the retro's `raw_text` (the retro summary) overwrites the user's original words. The user's note is preserved only if the retro engine successfully reads and includes it in the prompt context.
- **No `date` parameter on `POST /journal/entry`** — entries always write to `today_local()`. You cannot backfill a journal entry for a past date via the API; direct DB upsert is required.
- **`summary` column vs `retro_json.summary`** — `summary` (the column) is populated only by the interactive `save_journal_entry` tool. `retro_json["summary"]` is the retro engine's summary, stored in `raw_text`. These two paths never populate both columns simultaneously.
- **`retro_json` is a raw string** — not a structured column. If the retro engine returns malformed JSON, it is stored as-is and will cause JSON parse errors in any consumer.
- **Evening prompt doesn't trigger retro** — `_evening_prompt` at 10pm only sends a Telegram message; the retro is a separate unscheduled call. The retro is triggered by `orchestrator/retro.py`'s `generate_retro` function, which must be wired explicitly.
